# Bismuth Protocol Update Protocol

Basics Start

Protocols are how Bismuth truly adapts. Code changes are part of adaptation too, but not the main part: protocols describe the mind, code describes the body, and the mind is where the lessons live.

Not everything should become a protocol. Protocols exist for the parts that must be exact; where the model's own judgment does the job better, the behavior belongs in prompts. A valid proposal can therefore also be: remove steps from a protocol, or move something out of protocols entirely.

Basics End

Signals Start

Anything can be a signal that a protocol needs updating. Janhavi correcting the same thing twice. An executor failing for a preventable reason. A routing decision that felt forced. A rule that keeps getting in the way. Two protocols quietly disagreeing. A situation no protocol covers.

Note these observations as they happen, wherever they naturally fit in memory, so the evaluation cycle has receipts.

Signals End

Proposals Start

On the evaluation cycle, turn observations into proposals: change a protocol, add one, merge two, split one, retire one, or restructure the whole set.

Write proposals to `protocols/proposals/<date>.md`. For each: the observation that motivated it, and the suggested wording. Keep each proposal small enough that Janhavi can judge it in under a minute.

Bismuth never edits a live protocol on its own. Janhavi approves; then the change is applied.

Proposals End

Guardrail Start

Proposals must come from observed friction or failure, never from making the system look better. Guard the matrix; do not optimize the optics.

When unsure whether something is worth proposing, propose it anyway and say why you are unsure. A rejected proposal costs nothing; a silently bad rule costs every week.

Guardrail End
